# **Технічна архітектура та дослідницький звіт: UAV Watcher v2.0**

## **Керівне резюме**

Зростаюча потреба у стійкій локалізованій цивільній інфраструктурі безпеки в зонах конфліктів вимагає зміни парадигми в системах екстреного сповіщення. "UAV Watcher", система безпеки з відкритим вихідним кодом, що наразі працює в Кіровоградській області, представляє собою базову модель, яка використовує автоматизацію Telegram на базі Python та базову класифікацію загроз. Однак масштабування цієї системи до багатоплатформної архітектури національного рівня — при збереженні операційної цілісності в умовах сильно деградованого зв'язку — вимагає складного синтезу альтернативних протоколів зв'язку, архітектури "offline-first" (офлайн у пріоритеті) та психологічно вивірених інтерфейсів кризового реагування.

Цей комплексний дослідницький звіт оцінює технічні шляхи розвитку UAV Watcher до версії v2.0. Аналіз систематично розглядає впровадження програмованих сімейних груп безпеки, автономне відстеження місцезнаходження для пошуку постраждалих, формулювання кризових повідомлень, кросплатформні технічні обмеження та інтеграцію з існуючими екосистемами безпеки з відкритим кодом. Отримана архітектурна структура пропонує децентралізовану мікросервісну топологію, яка поєднує Telegram Bot API з mesh-мережами на базі LoRa, забезпечуючи високу доступність, локалізований суверенітет даних та інтуїтивно зрозуміле розгортання для нетехнічних користувачів, що діють у стресових бойових умовах.

## **1\. Сімейні групи безпеки через Telegram**

Інтеграція деталізованої, орієнтованої на сім'ю комунікації з питань безпеки в межах Telegram створює складні технічні проблеми через сувору антиспам-архітектуру платформи та межі прикладного програмного інтерфейсу (API). Стандартні реалізації повинні балансувати між HTTP-інтерфейсом Bot API та клієнтським API мобільного телекомунікаційного протоколу (MTProto).

### **Обмеження Bot API та обхідні шляхи MTProto**

Офіційний Telegram Bot API накладає свідомі обмеження для запобігання автоматизованим зловживанням і розповсюдженню спаму. Стандартний бот не може ініціювати розмову з користувачами, які самі не почали діалог з ним.1 Крім того, коли бот додається до стандартної групи, він за замовчуванням працює в "Приватному режимі" (Privacy Mode). У цьому стані бот "не бачить" загального трафіку розмов і отримує лише повідомлення, які починаються з команди через скіш, є прямими відповідями на власні повідомлення бота або прямо згадують ім'я користувача бота.2 Хоча Приватний режим можна вимкнути через адміністративний інтерфейс BotFather, бота потрібно видалити та знову додати до групи, щоб очистити кешований стан конфіденційності Telegram.2

Що ще важливіше, Bot API не має нативного ендпоінту для стандартних ботів, щоб програмно створювати супергрупи та запрошувати користувачів. Для досягнення справжнього програмного створення груп архітектура повинна використовувати Telethon — асинхронну бібліотеку Python, яка взаємодіє безпосередньо з MTProto API Telegram.3 Працюючи як "юзербот" (userbot) (автентифікуючись за допомогою API ID та API hash), система імітує легітимного клієнта.4 Це дозволяє програмно викликати AddChatUserRequest для примусового додавання контактів або ExportChatInviteRequest для генерації основних і додаткових посилань для приєднання.3 Однак використання юзерботів створює ризик алгоритмічних блокувань у разі порушення лімітів запитів, оскільки автоматизовані системи Telegram активно виявляють несанкціоновану автоматизацію через юзерботів.

Високоефективна архітектурна альтернатива для сімейного групування була представлена в Bot API 9.4: Приватні теми чату (Private Chat Topics).2 Ця функція дозволяє стандартним ботам створювати ізольовані гілки (теми) у стилі форуму безпосередньо в прямих повідомленнях (DM) один-на-один. Зберігаючи процес сімейного сповіщення у вигляді гілок в особистих повідомленнях замість створення зовнішніх супергруп, система повністю обходить обмеження на створення груп, гарантуючи, що окремі члени сім'ї отримують категоризовані сповіщення без необхідності адміністративного налаштування.2

### **Автоматизована перекличка (Rollcall) та процеси з Inline-кнопками**

Коли виявляється локалізована загроза, система повинна запустити автоматичну перекличку. Оптимальний паттерн користувацького досвіду використовує InlineKeyboardMarkup від Telegram. Бот транслює сповіщення з доданими кнопками зворотного виклику "Я в безпеці" (I'm Safe) та "SOS / Потрібна допомога" (SOS / Need Help).

Коли користувач натискає на inline-кнопку, клієнт Telegram відправляє CallbackQuery назад на сервер. Бэкенд обробляє ID користувача, оновлює локальний кеш SQLite з часовою міткою підтвердження, а потім редагує оригінальне повідомлення за допомогою editMessageText, щоб відобразити динамічно оновлюваний підрахунок. Telegram обмежує вихідні повідомлення бота до 30 на секунду 5; тому оновлення переклички під час масових подій повинні пакетуватися та відправлятися до API з інтервальними затримками, щоб запобігти виключенням 429 Too Many Requests.

### **Конфіденційність при обміні геоданими сім'ї**

Спільне використання геопросторових координат у сімейній групі вводить значні питання конфіденційності та операційної безпеки (OPSEC). Якщо користувач натискає кнопку "SOS", яка автоматично транслює його GPS-координати в чат Telegram, ці дані обробляються та зберігаються на пропрієтарних серверах Telegram. У зоні конфлікту централізоване агрегування даних є цінною мішенню для підтримуваних державою хакерів. Щоб пом'якшити це, архітектура повинна використовувати обфускацію на стороні клієнта. Замість передачі сирої широти та довготи через Bot API, локальний клієнт (що працює на Termux або як Android APK) може зашифрувати координати, використовуючи попередньо розподілений симетричний ключ серед членів сім'ї. Бот передає зашифрований рядок, і лише локальні клієнти членів сім'ї-одержувачів розшифровують і відображають координати на локальному інтерфейсі карти, забезпечуючи маршрутизацію через інфраструктуру Telegram з нульовим розголошенням (zero-knowledge).

### **P2P зв'язок (Peer-to-Peer) як резервний канал**

За сценаріїв, коли магістральна інфраструктура інтернету зруйнована, залежність від хмари Telegram робить систему неактивною. Архітектура повинна впровадити локалізований резервний варіант з використанням децентралізованих mesh-мереж. Шляхом підключення локального хоста Linux або Android Termux до радіо LoRa через Python API Meshtastic, система може маршрутизувати термінові SOS-повідомлення через mesh-мережу на частоті 900 МГц або 433 МГц. Демон на Python може перехоплювати локальні вводи та передавати їх за допомогою функції interface.sendText(), забезпечуючи локалізовану доставку навіть тоді, коли зовнішні ендпоінти API недоступні.6

## **2\. Пошук людей під завалами: Виявлення жертв після удару**

Руйнування багатоповерхових бетонних конструкцій внаслідок кінетичних ударів залишає цивільних осіб у пастці в середовищах, де традиційні комунікаційні парадигми не працюють. Пошук недієздатних осіб вимагає багаторівневого підходу до поширення радіочастот (РЧ), використання апаратного забезпечення та пасивного відстеження датчиків.

### **Пасивне виявлення запитів Wi-Fi (Probe Requests)**

Коли користувач опиняється під завалами, функціональність GPS припиняється негайно через сильне згасання сигналу діапазону 1,575 ГГц через бетон та арматуру. Однак, навіть коли смартфон відключений від стільникових вишок і мереж Wi-Fi, його мережева карта постійно передає керуючі кадри стандарту 802.11 (probe requests), шукаючи відомі ідентифікатори мереж (SSID).

Сучасні операційні системи, зокрема iOS 14+ та Android 10+, використовують рандомізацію MAC-адрес (Media Access Control) для запобігання постійному відстеженню через ці кадри.7 Ця рандомізація спричиняє значне спотворення даних у стандартній Wi-Fi аналітиці. Розширені архітектури відстеження обходять це шляхом вилучення інформаційних елементів з керуючих кадрів probe request і аналізу багатовимірного простору індикатора рівня отриманого сигналу (RSSI). Застосовуючи алгоритми неконтрольованого машинного навчання до цих конкретних точок даних, рятувальні команди, що використовують локалізовані приймачі, можуть створювати "відбитки" (fingerprints) та відстежувати фізичну присутність непідключених пристроїв Wi-Fi під завалами, ефективно обходячи захист від рандомізації MAC.7

### **Mesh-мережі Bluetooth Low Energy (BLE) та акустичні маяки**

Bluetooth Low Energy (BLE) забезпечує вторинний вектор проникнення через щільні матеріали. Існуючі програми використовують BLE для створення ad-hoc mesh-мереж, дозволяючи пристрою, що потрапив у пастку, ретранслювати свій пропрієтарний ідентифікатор через інші пристрої поблизу, поки він не досягне активного крайового вузла, підключеного до інтернету.

Акустичне виявлення слугує критично важливим резервом, коли РЧ сигнали повністю поглинаються структурною масою. Смартфони можна запрограмувати на трансляцію специфічних акустичних частот через внутрішні динаміки. Низькочастотний підчутний механічний резонанс або високопроникні пульсуючі тони є дуже ефективними. Рятувальні команди, оснащені сейсмічними акустичними датчиками, можуть тріангулювати ці викиди більш ефективно, ніж людську вокалізацію, яка виснажує фізичну енергію жертви, викликає зневоднення та погано проходить через тверду масу.

### **Кнопка "Мертва людина" (Dead Man's Switch) та оптимізація батареї**

Функція "Мертва людина" автоматично транслює останні відомі координати користувача через SMS або LoRa, якщо він не взаємодіє з пристроєм після заданого інтервалу після удару. Реалізація цього вимагає можливостей фонової обробки. На Android для цього потрібен Foreground Service (Фоновий сервіс) у поєднанні з постійним сповіщенням і частковими блокуваннями WakeLocks, щоб запобігти призупиненню процесора операційною системою.

Однак безперервне опитування місцезнаходження та активна передача РЧ викликають серйозне теплове навантаження та швидке розрядження акумулятора. Стратегії оптимізації батареї вимагають обходу режиму Doze в Android за допомогою AlarmManager.setExactAndAllowWhileIdle. Щоб запобігти непотрібному розрядженню, архітектура повинна покладатися на інерціальний вимірювальний блок пристрою (IMU) для виявлення раптового припинення руху. Протокол SOS запускається лише тоді, коли ідентифіковано профіль удару, після якого йде нерухомість, що зберігає заряд батареї пристрою для тривалого випромінювання сигналу маяка.

## **3\. Шаблони чат-ботів для кризового реагування та психологічна архітектура**

Ефективність системи екстреного попередження визначається не лише швидкістю її передачі, але й психологічним сприйняттям її корисного навантаження. Погано сформульоване попередження може викликати параліч або паніку, зводячи нанівець технологічну перевагу раннього попередження. Дизайн повинен інтегрувати офіційні державні рекомендації з перевіреними когнітивно-поведінковими рамками.

### **Архітектура Командування тилу (Pikud HaOref)**

Командування тилу Ізраїлю забезпечує найбільш перевірений у бойових умовах шаблон архітектури цивільного попередження. Система уникає загальнонаціональної паніки шляхом розподілу географічного ландшафту на приблизно 1700 окремих багатокутників сповіщення (polygons).8 Коли виявляється запуск, алгоритми аналізу траєкторії на основі штучного інтелекту розраховують ймовірну зону удару за лічені секунди, активуючи сирени та мобільні сповіщення виключно в цільових багатокутниках.9 Це надає цивільним особам точне вікно від 15 до 90 секунд для пошуку укриття, мінімізуючи економічні та соціальні зриви.8 Технічний стек, що підтримує це, покладається на ізольовані мікросервіси, що взаємодіють через протокол MQTT, гарантуючи, що сплеск сповіщень безперебійно обробляється через легковаговий проксі, який опитує первинний API кожні три секунди, створюючи єдине джерело правди без перевантаження зовнішніх ендпоінтів.10

### **Психологічне форматування попереджувальних повідомлень**

При написанні тексту для користувачів, які відчувають гострий стрес або панічні атаки, когнітивне навантаження повинно бути радикально мінімізовано. Особи в стані паніки демонструють погіршення розуміння прочитаного, дефіцит робочої пам'яті та потребують суворих, авторитетних, але глибоко заспокійливих структурних форматів.

Початкове повідомлення повинно встановлювати негайну присутність і фізичну реальність. Відповіді повинні використовувати просту, неосудливу мову, зосереджену на негайному комфорті, таку як "Я тут з тобою. Ти в безпеці. Це мине".11 Контрпродуктивні фрази, які знецінюють емоційний стан, такі як "просто заспокойся", "розслабся" або "ти занадто гостро реагуєш", повинні бути суворо заборонені в лексиконі чат-бота.11

Автоматизовані відповіді повинні плавно переходити до технік "заземлення", щоб перенаправити неврологічний фокус із внутрішніх відчуттів паніки на зовнішні подразники. Метод 5-4-3-2-1 є дуже ефективним, коли доставляється послідовно через текст: інструктаж користувачеві назвати п'ять речей, які він може побачити, очікування відповіді та перехід до чотирьох речей, яких він може торкнутися.11 Дихальні вправи повинні бути аналогічно розділені для контролю темпу. Чат-бот повинен видавати незалежні повідомлення, синхронізовані із заданою частотою дихання, наприклад: "Повільно вдихайте на 4 рахунки... 1... 2... 3... 4", за чим слідує вторинне повідомлення про затримку дихання, і третє \- про видих.11 Екстрені попередження повинні бути послідовними, конкретними та чітко визначати, які дії слід вжити, не залишаючи інформаційних прогалин.14

### **Офіційні шаблони протоколів для конкретних загроз**

Інтеграція міжнародних гуманітарних рамок є життєво важливою. Всесвітня організація охорони здоров'я (ВООЗ) та Управління ООН з координації гуманітарних питань (UN OCHA) наголошують на важливості мереж раннього попередження на рівні громад, які ставлять у пріоритет чіткість вектора загрози. Протоколи укриття Міжнародної федерації товариств Червоного Хреста і Червоного Півмісяця (IFRC) диктують конкретні модифікації середовища, такі як використання клейкої стрічки та щільної поліетиленової плівки для герметизації дверей і вентиляційних шахт від хімічного диспергування.

UAV Watcher повинен пов'язувати класифіковані ШІ загрози з чіткими інструкціями щодо ухилення в залежності від типу кінетичної загрози:

* **Шахед / БПЛА-камікадзе:** Характеризується чіткою низькочастотною акустичною сигнатурою та відносно повільною швидкістю баражування. Сповіщення повинно вказувати користувачам дотримуватися "правила двох стін" (розміщення двох несучих стін між собою та зовнішньою стороною) та уникати квартир на верхніх поверхах через характеристики фугасного заряду, призначеного для поверхневої детонації.  
* **Крилата ракета Калібр:** Траєкторії польоту з обгинанням рельєфу, призначені для уникнення радарів. Час попередження сильно варіюється. Інструкції повинні вимагати негайного спуску до підземних укриттів, оскільки стандартні житлові несучі стіни є недостатніми проти кінетичної маси та потужності вибуху.  
* **Балістична ракета Іскандер:** Гіперзвукова швидкість на термінальній ділянці залишає мізерно малий час для попередження (часто менше двох хвилин). Повідомлення має бути відформатоване з максимальним пріоритетом, замінюючи беззвучні режими (там, де це можливо), та інструктуючи до негайного маневру "впасти і накритися" подалі від скла, якщо підземні укриття недоступні.  
* **Плануюча бомба КАБ/ФАБ:** Величезна потужність вибуху, що призводить до глибокого утворення кратерів і повного руйнування конструкцій житлових кварталів. Правило двох стін є абсолютно неефективним. Сповіщення, що вказують на траєкторію плануючої бомби, повинні чітко наказувати евакуюватися в глибоко армовані багаторівневі підземні бетонні бункери.

## **4\. Обмеження багатоплатформної архітектури**

Розгортання UAV Watcher у середовищах Android, iOS та Linux вимагає архітектури, яка збалансовує кросплатформну ефективність розробки з глибоким доступом до апаратного забезпечення для функцій виживання.

### **React Native проти Flutter проти Progressive Web Apps (PWA)**

Прогресивний веб\-додаток (PWA) пропонує перевагу єдиної кодової бази, доступної через будь-який сучасний браузер, використовуючи Service Workers для кешування основних активів HTML, CSS і JavaScript для офлайн-доступу. Однак PWA стикаються з нездоланними обмеженнями щодо функцій екстреної безпеки в екосистемі iOS від Apple. WebKit від Apple обмежує фонову синхронізацію, а доступ до Push API вимагає від користувача вручну додати додаток на головний екран. Більше того, фонове відстеження місцезнаходження — обов'язкова умова для геозонних сповіщень та функції "Мертва людина" — заборонено для PWA, що працюють на iOS.

Для досягнення фонового відстеження місцезнаходження та надійних push-сповіщень, які можуть перевизначати апаратні беззвучні перемикачі, обов'язковою є нативна оболонка (native wrapper).

* **React Native** використовує мостову архітектуру для виклику нативних віджетів виробників оригінального обладнання (OEM). Це дозволяє бездоганно інтегрувати модулі фонового розташування, але може внести затримку під час високочастотного опитування датчиків.  
* **Flutter** компілюється в нативний код ARM і використовує власний механізм рендерингу Skia (або Impeller). Він забезпечує дуже узгоджені користувацькі інтерфейси на різних платформах і чудову продуктивність для складного рендерингу карт (життєво важливо для офлайн-маршрутизації OpenStreetMap).

Комерційні додатки безпеки, такі як Everbridge, AlertMedia та Rave Mobile Safety, обходять ці обмеження, працюючи як глибоко інтегровані корпоративні платформи "програмне забезпечення як послуга" (SaaS). Вони використовують мультимодальні системи доставки, в першу чергу покладаючись на технологію стільникового мовлення на рівні оператора (Cell Broadcast), SMS-шлюзи (наприклад, Twilio) та push-сповіщення нативних додатків через службу сповіщень Apple (APNs) та Firebase Cloud Messaging (FCM). Оскільки UAV Watcher є низовим проектом з відкритим вихідним кодом без інтеграції телекомунікаційних операторів, він повинен імітувати цю мультимодальну доставку, поєднуючи MTProto-push Telegram, резервне SMS-кодування та локалізовані трансляції LoRa.

### **Офлайн-перша архітектура (Offline-First) та обмеження ОС**

Офлайн-перша архітектура повинна припускати, що підключення до інтернету є винятком, а не нормою. Клієнтська програма повинна використовувати вбудовану базу даних SQLite (для нативних програм) або IndexedDB (для PWA). Усі вихідні зміни стану, такі як підтвердження переклички або спрацьовування SOS, записуються в локальну чергу мутацій. Адаптер фонової синхронізації відстежує стан мережі через мережевий стек операційної системи. Після відновлення з'єднання черга послідовно скидається до backend API.

Якщо основний API недоступний, адаптер синхронізації переходить на альтернативні транспорти, такі як кодування SMS або послідовна передача до локалізованого вузла Meshtastic LoRa. Робота у фоновому режимі вимагає навігації через суворі заходи збереження заряду акумулятора на рівні ОС. На Android додаток має запитувати дозвіл ACCESS\_BACKGROUND\_LOCATION і запускати Фоновий сервіс (Foreground Service) з активним сповіщенням. В iOS виконання у фоновому режимі суворо обмежене; програма повинна запитувати дозвіл на визначення місцезнаходження "Завжди" (Always) і використовувати службу значних змін місцезнаходження (Significant Location Change), якій бракує високочастотної точності, необхідної для негайної активації перемикача "Мертва людина" після удару, що є значним обмеженням для користувачів Apple у зонах конфлікту.

## **5\. Інтеграція з існуючими Open Source екосистемами**

UAV Watcher v2.0 не повинен існувати у вакуумі; він повинен безперешкодно інтегруватися з існуючою цифровою оборонною інфраструктурою України та глобальними протоколами безпеки з відкритим кодом, щоб посилити свою ефективність і зменшити дублювання інженерних зусиль.

### **API Alerts.in.ua та існуючі українські додатки**

Сервіс alerts.in.ua діє як основний агрегатор офіційних статусів повітряної тривоги в Україні. Він надає RESTful API, що повертає корисні навантаження JSON з детальною інформацією про активні загрози в областях, районах і окремих громадах.15 API вимагає авторизаційного токену (bearer token) і надає доступ до таких ендпоінтів, як /v1/alerts/active.json, які деталізують назву місця, тип тривоги (повітряна тривога, артилерійський обстріл, вуличні бої, хімічна загроза) та високоточні мітки часу початку.15 Інтеграція цього API дозволяє UAV Watcher здійснювати перехресні посилання локалізованої розвідки на основі відкритих джерел (OSINT) каналів Telegram з офіційними державними попередженнями, використовуючи aiohttp для Python або виділений асинхронний клієнт alerts\_in\_ua.15

Існуючі програми, такі як "єТривога" та "Повітряна тривога", ефективно обробляють масові трансляції, але не мають функцій детальної переклички на рівні сім'ї, запропонованих для UAV Watcher. Отримуючи дані з тих самих державних API, UAV Watcher забезпечує узгодженість, додаючи при цьому локалізовані рівні виживання.

### **Автоматизація інфраструктури та OpenStreetMap**

Інтеграція середовищ фізичної безпеки може автономно захищати цивільних осіб. Ajax Systems, провідний постачальник обладнання для безпеки у Східній Європі, надає можливості інтеграції, які дозволяють серверам домашньої автоматизації зчитувати стани датчиків, а також ставити/знімати системи з охорони.17 Однак існують архітектурні обмеження: потокове передавання подій у реальному часі (через Server-Sent Events або AWS SQS) є активним лише тоді, коли система Ajax знаходиться під охороною. Коли вона знята з охорони, API покладається на інтервали опитування (зазвичай 5 секунд для дверей і 30 секунд для датчиків руху).18 Інтеграція UAV Watcher із мостом Ajax дозволяє системі автоматично блокувати електронні засуви, опускати вибухозахисні віконниці або активувати вторинні фізичні сирени, коли локалізована загроза підтверджується ШІ-класифікатором.

Для автономної навігації до безпечного місця важлива інтеграція даних OpenStreetMap (OSM). Використовуючи Overpass API, UAV Watcher може запитувати amenity=shelter або bunker\_type=hardened для завантаження даних вузлів. Ці дані GeoJSON кешуються локально на пристрої, дозволяючи додатку відображати вектори маршрутизації до найближчого бункера, навіть якщо стільникова інфраструктура зруйнована.

### **Децентралізовані протоколи: Matrix та Meshtastic**

Покладання виключно на Telegram вводить єдину точку відмови. Протокол Matrix (і його основний клієнт Element) пропонує децентралізовану, федеративну альтернативу. Matrix використовує криптографічні механізми (ratchets) Olm і Megolm для забезпечення наскрізного шифрування. Незважаючи на те, що прийняття користувачами є нижчим, ніж у Telegram, підтримка вебхуків Matrix гарантує, що у разі гео-блокування Telegram або збою його інфраструктури, UAV Watcher може продовжувати направляти повідомлення через власні сервери (homeservers) Matrix.

Для зон серйозних катастроф, які переживають повне відключення інфраструктури, Meshtastic забезпечує автономний децентралізований зв'язок за допомогою доступних радіостанцій LoRa на базі ESP32.19 Мережа працює без центральних маршрутизаторів, використовуючи протокол маршрутизації лавиною (flood-routing), де кожен вузол повторює сигнал. API Meshtastic для Python дозволяє пристрою підключатися через послідовний порт (/dev/ttyUSB0) або протокол керування передачею (TCP), що дозволяє автоматизованим сценаріям впроваджувати текстові повідомлення в mesh-мережу за допомогою команди interface.sendText("payload").6

Крім того, інтеграція з цивільними варіантами Android Team Awareness Kit (ATAK) через Multicast User Datagram Protocol (UDP) і XML-повідомлення Cursor on Target (CoT) дозволяє координаторам цивільної оборони бачити сповіщення UAV Watcher і маяки SOS, які динамічно накладаються на тактичні карти.

## **6\. Рекомендована технічна архітектура (v2.0)**

Щоб відповідати суворим вимогам щодо високої доступності, глибокої інтеграції платформ і автономної стійкості в умовах зони бойових дій, рекомендована архітектура для UAV Watcher v2.0 дотримується моделі мікросервісів Hub-and-Spoke (центр-і-спиці).

**1\. Локальний хаб (Linux / Android Termux):**

Ядром обробки залишається локалізований демон Python. Розгортання через Termux дозволяє нетехнічним користувачам встановити систему за допомогою одного bash-скрипту (pkg install python && pip install uav-watcher). Це гарантує, що навіть якщо з'єднання з зовнішніми хмарними провайдерами розірвано, локальний вузол продовжуватиме обробляти логіку. Він запускає асинхронний цикл подій asyncio, керуючи кількома вхідними та вихідними потоками.

**2\. Агрегатори вхідних даних (Спиці):**

* **Монітор OSINT:** Клієнт на основі Telethon, який скрейпить локалізовані канали Telegram щодо акустичних звітів про безпілотники "Шахед" та безпосередні кінетичні загрози.  
* **Офіційний полінг API:** Асинхронний клієнт, що опитує API alerts.in.ua на предмет регіональних змін статусу.  
* **Mesh Listener:** Послідовний слухач, підключений до локального вузла Meshtastic через USB, який відстежує вхідні пакети LoRa SOS.

**3\. Ядро обробки та ШІ:**

Вхідні необроблені дані нормалізуються і передаються у легковагову, локально розміщену Велику мовну модель (або OpenAI-сумісний API, якщо дозволяє мережа). Цей ШІ-модуль аналізує неструктурований текст Telegram для вилучення векторів загроз, даних координат і рівнів терміновості, зіставляючи їх із заданою геозоною користувача.

**4\. Механізм сповіщень та керування станом:** Механізм перевіряє координати загрози відповідно до конфігурацій користувача. Сповіщення розсилаються через Telegram Bot API з використанням Приватних тем чату (Private Chat Topics), щоб обійти обмеження конфіденційності групи.2 Дані переклички (rollcall) обробляються за допомогою локального екземпляра SQLite, що забезпечує суверенітет даних. Якщо Telegram API недоступний (ConnectionError), рушій динамічно перемикається на послідовний інтерфейс Meshtastic для трансляції сповіщення через локальну РЧ mesh-мережу.

async def generate\_family\_group\_link(group\_identifier: str) \-\> str:  
    """  
    Connects to the MTProto API, retrieves the group entity, and exports an invite link.  
    Requires the userbot to have administrative privileges in the target group.  
    """  
    \# Initialize the asynchronous MTProto client  
    async with TelegramClient(SESSION\_NAME, API\_ID, API\_HASH) as client:  
        try:  
            \# Resolve the entity. Can be a username, phone number, or existing link \[20\]

        except ChatAdminRequiredError:

            return None  
        except Exception as e:  
            \# Catching generic exceptions for network drops or API rate limits  
            print(f"Network or API exception occurred: {e}")  
            return None

import time

import meshtastic.serial\_interface  
from pubsub import pub

class MeshAlertBridge:  
    def \_\_init\_\_(self, serial\_port='/dev/ttyUSB0'):  
        """  
        Initializes the Meshtastic serial interface and subscribes to mesh events.  
        Assumes the radio is connected via OTG cable to an Android device running Termux,  
        or directly to a Linux single-board computer.  
        """  
        try:  
            \# Establish serial connection to the LoRa radio  
            self.interface \= meshtastic.serial\_interface.SerialInterface(devPath=serial\_port)  
            print("Connected to local LoRa mesh node.")  
              
            \# Subscribe to incoming packets for 2-way communication \[21\]  
            pub.subscribe(self.on\_receive, 'meshtastic.receive')  
        except Exception as e:

    def on\_receive(self, packet, interface):  
        """Callback for incoming packets. Filters for text messages.\[21\]"""  
        try:  
            \# Verify the packet contains decoded text payload  
            if 'decoded' in packet and packet\['decoded'\]\['portnum'\] \== 'TEXT\_MESSAGE\_APP':  
                payload \= packet\['decoded'\]\['payload'\].decode('utf-8')  
                print(f"INCOMING MESH ALERT: {payload}")  
                \# Logic to forward to local UI, SQLite DB, or trigger acoustic beacon goes here  
        except KeyError as e:  
            pass \# Ignore non-text telemetry packets (e.g., node info, GPS position)

    def broadcast\_alert(self, threat\_message: str):  
        """Transmits a text payload to the default broadcast channel."""  
        try:  
            print(f"Transmitting to mesh: {threat\_message}")  
            self.interface.sendText(threat\_message)  
        except Exception as e:  
            print(f"Transmission failed: {e}")

## **9\. Аналіз ризиків та стратегія пом'якшення**

Розгортання систем, від яких залежить життя, у висококонкурентних кібер- та фізичних середовищах створює серйозні операційні ризики. Надійна архітектура повинна проактивно пом'якшувати ці вразливості.

### **Обмеження частоти запитів Bot API (Rate Limiting) та алгоритмічні блокування**

**Ризик:** Telegram застосовує суворі обмеження швидкості (зазвичай 30 повідомлень на секунду або 20 повідомлень на хвилину в певних групах).5 Під час масового сповіщення про балістичні траєкторії, одночасне опитування сотень членів сім'ї призведе до помилок 429 Too Many Requests, що спричинить втрату критичних попереджень. Крім того, використання юзерботів Telethon порушує Умови надання послуг Telegram, якщо вони розпізнаються як спам, що призводить до постійного блокування номера телефону. **Пом'якшення:** Механізм сповіщень повинен впроваджувати суворий обмежувач швидкості за принципом маркерного кошика (token-bucket). Сповіщення повинні ставитися в чергу та оброблятися з максимальною пропускною здатністю 25 повідомлень на секунду. Функціональність юзербота повинна суворо обмежуватися низькочастотними адміністративними завданнями (генерація посилань), а не масовим розсиланням повідомлень.

### **Зловживання інфраструктурою з боку зловмисників та шкідливе ПЗ**

**Ризик:** Зловмисники активно атакують довіру цивільного населення до додатків для сповіщень. Кампанії, такі як "Операція Фальшива сирена" (Operation False Siren), включали розповсюдження шпигунського програмного забезпечення для Android, що імітувало офіційні ізраїльські програми для сповіщень (Red Alert), надсилаючи бездоганно перекладені зловмисні SMS-повідомлення жертвам.22 Крім того, боти Telegram часто кооптуються як приховані канали командування і контролю (C2) розвиненими стійкими загрозами (APT).23 **Пом'якшення:** Android APK UAV Watcher має бути криптографічно підписаний і поширюватися виключно через перевірені репозиторії (F-Droid або GitHub Releases) з опублікованими хешами SHA-256. Система ніколи не повинна виконувати код, переданий через вхідні дані Telegram, нейтралізуючи доставку шкідливих навантажень через ботів.

### **Компрометація проксі-серверів для апаратних мостів**

**Ризик:** Під час інтеграції зі сторонніми API (наприклад, Ajax Systems) без офіційних корпоративних ключів трафік часто маршрутизується через проксі-сервери спільноти. Скомпрометований проксі може перехопити хеш облікових даних, надаючи адміністратору проксі повний доступ для зняття систем фізичної безпеки з охорони або підробки даних датчиків.18 **Пом'якшення:** Архітектура повинна застосовувати наскрізне шифрування. Якщо потрібні проксі-сервери спільноти, UAV Watcher повинен використовувати Прямий режим (Direct Mode) з офіційними корпоративними ключами API, коли це можливо, суворо обминаючи неперевірені проміжні вузли.18
